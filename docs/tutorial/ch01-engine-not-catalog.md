# ch01 引擎而非目录

> 本章是《机器学习审阅者指南》的立场章,没有代码。读完你应该能判断:这份清单(以及你手上的任何一份库清单)到底该当目录用,还是当引擎用。

## 1. 半小时交付的完整管线

场景不复杂,任何一个做过业务的人都能复述:客户流失率太高,运营团队想要一个"下个月可能流失的客户名单",好让他们提前打电话挽留。你把需求写给 AI——"用历史客户数据训练一个流失预测模型,输出高风险客户名单,评估用 AUC"——四十分钟后回来的是一整套东西:数据加载、缺失值填充、标准化、独热编码、逻辑回归、交叉验证、ROC 曲线、阈值扫描、CSV 导出。代码风格干净,注释齐全,测试通过,AUC 0.93。

评审会上没有一个人反对。数据是历史快照,标签是"未来 30 天内是否取消",切分是标准的 8:2,指标是行业里最常被汇报的那个。模型上线,每天导出名单,客服按分数从高到低打电话。

六周后复盘:拨打量没变,续费率没变,名单里高分客户和随机抽的客户在真实流失率上没有差别。模型是准的——它精准地预测了"历史上什么样的人会流失"。

问题不在代码。代码完全正确。问题在字段的时点:数据表里有一列 `last_cancel_plan_change`,记录客户最近一次变更套餐的时间——而这份快照是每周日凌晨从运营库导出的,**变更记录要到第二天早上才同步进来**。这列字段在预测时点是不存在的,却安静地躺在训练表里。模型用它预测"未来 30 天会不会取消",而它恰恰记录的是"最近一次已经发生的套餐变更"。AUC 0.93 里有多少来自这一列?没人算过,因为没人问过。

同一张表里还埋着第二个问题:名单按分数从高到低拨打,而高分客户里有一批是**最近 30 天内主动填过满意度问卷的人**——他们本来就更可能被客服联系到,也更容易被留住。模型的分数和"更容易被留下"之间,隔着一个反向因果。

这是一类事故最难缠的地方:它没有任何报错。测试通过,指标达标,数据管线健康检查一片绿。唯一能发现它的动作,是有人问了一句"预测那一刻,这个字段存在吗"。

## 2. 价值曲线倒转

有一件事在 2023 年之前需要一位资深工程师两周,现在需要 AI 三分钟:**把 API 返回的嵌套 JSON 拍平成表格、对齐时间戳、处理缺失值、把训练结果写成一段能发周报的 Markdown**。这些是胶水代码:没有判断,没有取舍,没有对业务后果的承担。它们的价值曲线在往下掉,掉到底之后不是"没用",是**成本趋近于零**——这才是它真正危险的地方。当一段代码的成本趋近于零,人们就不再审它了,直到它连着某个不透明的假设一起流进生产。

同时有三件事在往上涨,而且很难被 AI 替代:

**定义问题。**"预测流失"是一个假问题,真问题是"在有限坐席产能下,打电话给谁能把续费率抬高 X 个百分点"。后者才有可解的形式——它隐含着成本、产能、时间窗、动作的因果假设,以及"不打电话会怎样"的反事实。AI 写不出这个,因为这个结论不在任何文档里,只在你对业务的理解里。

**守住原理门槛。**泄漏、切分、指标、校准、分布漂移——这些概念不随框架更替而过时,也不随模型规模而变得不重要。恰恰相反,模型越强,泄漏的后果越大:一个满分模型会让人停止怀疑,而一个平庸的模型至少还会被人质疑。

**审阅能力。**这是本书要训练的东西。审阅不是"读代码找 bug",而是在代码"能跑"的前提下判断它"做的是不是对的事"。前者可以用静态检查和测试覆盖,后者只能靠人对因果、时序、代价、分布的理解。

顺带说清一件容易被误解的事:价值曲线倒转不等于"AI 取代工程师"。它取代的是**执行**,不是**裁决**。而裁决的位置,恰恰因为执行变便宜而变得更值钱——因为你一个下午能审的产出,比三年前多出二十倍。

## 3. 危险的失效模式

下面三种形态共享一个结构:**代码正确、指标达标、事情做错**。它们都不会抛异常,只会在生产里安静地烧钱。

**target leakage(标签泄漏)。**特征里混进了预测时点还不存在的信息,或者标签本身是特征的副本。识别它的唯一方法是逐字段问"在我做预测的那一刻,这个值拿得到吗",而不是看 AUC 有多漂亮。

> 为什么不懂原理看不出来:因为程序能跑。泄漏字段是表里真实存在的一列,读取它不需要任何特殊操作;AUC 会诚实地报出 0.99,不会附一行"这个数字没有意义"。

**指标代理失真(metric proxy distortion)。**离线指标与业务结果之间不是恒等映射。代理指标一旦被当作目标优化,就会被优化到失真:客服团队把呼叫量当 KPI,名单分数就被用来"挑最好打的客户",AUC 完全不动,拨打量涨了 40%,续费率掉了 1 个点。

> 为什么不懂原理看不出来:因为程序能跑。`roc_auc_score` 不知道你的业务;你写进需求里的"AUC"这个词,在代码里只是一个数字。**指标是业务的代理,代理会失真,而这个失真在代码里没有任何表示形式。**

**时序穿越(temporal cross-contamination)。**随机切分把"未来"混进了训练集。预测 2026 年的销量,训练集里却包含了 2026 年 3 月的数据——那是未来,只是相对于"数据快照时刻"的过去。模型学到的是"这个月已经卖了多少",而这在真实预测时拿不到。

> 为什么懂原理也常看不出来:因为程序能跑,切分 API 只接受一个 `test_size` 参数,默认 `shuffle=True`,它不会警告你业务数据有严格的时间方向。

三种形态的共同处方只有一个:**在把指标当成事实之前,先问这个数字是从哪一步算出来的**。这也是本清单每个类目 subtitle 里那句 "Gate your review on: ..." 想说的同一件事——每个领域都有它自己最致命的那道门槛。

## 4. 本清单的用法

`config/header.md` 的立场段(README 每次生成时嵌在正文之前)写着一句关键的话:这份清单是 **a map of solution paradigms and the principles you must hold in order to direct and review AI-generated ML code — not an API directory**。这句话不是修辞,是对使用方式的硬性要求。目录的用法是查"哪个库能做 X",引擎的用法是先定"X 到底该是什么",再决定要不要车。

落到日常,四个姿态:

**先业务问题,后工具。**每个类目开头那句 "For &lt;业务问题&gt;" 就是入口。先用业务语言描述问题,再让它把你映射到类目。顺序反过来,你会在搜索结果里挑一个"看起来能跑"的东西,然后花两周时间给一个错的模型找特征。

**握住把关原理。**每个类目还写了 "Gate your review on: &lt;原理门槛&gt;"。那是审阅该类目 AI 产出的准入线:不懂这条原理,你就没有能力判断 AI 给的代码是否可信,只能选择相信或者不信——两个都是坏选择。

**用审阅清单,而不是用直觉。**[REVIEW-CHECKLISTS.md](../../REVIEW-CHECKLISTS.md) 为 13 个核心类目各列了一组问题("What exactly is being predicted, and does the label exist at prediction time in production?"),外加一节 `## Categories where the review is mostly engineering hygiene` 覆盖其余类目。审阅时逐条问,不要凭手感。直觉会被"代码写得很漂亮"污染,问题不会。

**机器管机械正确性,人管判断。**本仓把 `scripts/validate.py` 插在了定时生成流水线的前一步——结构性的错(重复 `name`、缺 `name`、未定义标签、畸形 `github_id`)由机器拦下,人只需要盯着"这个问题值不值得做""这个类目归属对不对"。这条分工线要画清楚:机械的东西全自动化,判断的东西全留给人。第 5 节就是这个分工的现场。

## 5. 本仓的实演:2026-10-03 的一次改造

上面四句话在本仓库有真实记录。2026 年 10 月 3 日(周六)下午,我们把这份清单从"库目录"改造成"解法范式 + 审阅原理地图"。真实的过程,正好演示了两件事:机械检查必须机器做,以及机械检查的**误报**本身也需要原理。

那天 15:53,第一个 commit 加了 `scripts/validate.py`——一个检查 `projects.yaml` 结构的校验器。规则一共五条:四个顶层键都在、每个项目有唯一 `name`、`github_id` 形如 `owner/repo`、显式 `category` 必须在 `categories:` 块里定义、显式 `labels` 的每个元素是已定义标签。

六分钟后的第二个 commit 修了校验器的两个真 bug:把 `others` 当作隐式合法兜底;以及在遍历 `labels` 前先做类型检查。**注意这两处都是校验器自己的错,不是数据的错**——一个检查工具如果不知道自己领域里的合法约定,它报出来的错就有一半是噪声,而噪声会让人开始忽略它的输出。这是"机械检查也需要原理"的第一个含义。

把修好的校验器指向真实数据,它报出 **11 条错误**。逐条看,这 11 条对应的是 8 个根因:

- **4 个标签定义缺失。** `spacy`、`huggingface`、`keras`、`xgboost` 四个标签在 `labels:` 块里根本没定义,却被 7 个项目引用——所以报出 7 条 `undefined label`。7 条错误,1 个根因。
- **2 处重名。** `Orbit`(#871)和 `torchrec`(#904)各自与更早的条目同名,重复的 `name` 会让生成器无法唯一定位条目。
- **1 处缺 `name`。** 编号 #928 的条目(后来补上名字,成了 `neurolink`)压根没有 `name` 键。
- **1 处类型错。** litellm 写的是 `labels: others`——裸字符串,不是列表。

**litellm 这一处值得单独说。**它在第一版校验器上产生了 **6 条假阳性**:`undefined label 'o'`、`'t'`、`'h'`、`'e'`、`'r'`、`'s'`。原因是那行代码写的是 `for label in proj.get("labels") or []`——Python 把字符串当序列,**逐字符**迭代,于是 "others" 被拆成 o-t-h-e-r-s 六个"标签"去查表。真实问题是"类型不对",诊断却变成"这六个标签都没定义"。六条报错,零条有用信息。补上 `isinstance(labels, list)` 之后,它收敛成一条准确的:`project 'litellm': labels must be a list (got str)`。

一个教训:**校验器给出的报错行数不等于问题的个数**。这里 11 条报错背后是 8 个根因;如果修第一版校验器,还会再多出 21 条 `undefined category 'others'` 的假阳性(累计 37 条)。审阅报错的方式必须是从上往下归类找根因,而不是从下往上逐条改。

现在说"延迟暴露"。`projects.yaml` 每一项的下游是每周四 14:00 UTC 的定时生成(`cron 0 14 * * 4`,东八区周四晚上 22:00),生成 README、`latest-changes.md` 和 `history/` 快照。10 月 3 日是周六。**如果那时没有校验层,这 11 处缺陷会一直躺在数据里,直到 10 月 8 日(周四)晚上那次定时任务才第一次真正去渲染它们**——而失败点会出现在生成器里,报错信息指向生成器,排查者会先去怀疑上游工具,而不是自己的数据。数据到出问题隔了 5 天,代码到出问题隔了 0 行。

当天 18:33 的 commit 把 `validate.py` 插进了 CI,放在生成步骤**之前**。缺陷从"周四深夜爆炸"变成"提交时红灯"。**这就是第 4 节那条分工线**:结构性正确性交给机器,判断留给人——而前提是,交给机器的那个机器,得先被审一遍。

## 6. 五条工作原则

原则如果不能执行,就是装饰。以下五条都带可检查的动作。

**一、定义问题先于选工具。**动手前,用业务语言写出三句话:预测什么、预测的那一刻能拿到什么数据、按预测结果采取的行动是什么。做不到第三句,说明你还没有一个优化问题,只有一个相关性游戏。**检查动作**:把这三句话写进 issue 或 commit message,让半年后的自己能看到当时的判断。

**二、手写一次最小实现。**每个你要用 AI 加速的领域,先自己手写 50–150 行的最小版本,纯 Python 标准库,不加任何库。手写的目的不是取代 AI,而是**建立错误基线**——你必须亲眼见过一个逻辑回归是怎么从 sigmoid 和梯度下降长出来的,才能在 AI 交回来的代码里认出"它少了 L2 正则""它把标签也当成了特征"。**检查动作**:`code/chXX/chXX_minimal.py` 能跑,并打印出你要用来对照的量(权重、混淆矩阵、排序质量)。

**三、AI 产出必须过审阅清单,不能过测试。**测试回答"代码是否按写的做",清单回答"这件事是否该这么做"。拿到 AI 产出的第一件事,是打开 [REVIEW-CHECKLISTS.md](../../REVIEW-CHECKLISTS.md) 对应类目那一节,逐条问出答案,并把答案记进 commit 或 PR。**检查动作**:PR 里有一段文字回答了至少一条 "Review before trusting AI code" 的问题;如果没有,那不是 AI 产出被接受了,是它被漏审了。

**四、指标必须翻译到业务语言。**写进需求文档的每个指标,都要附一句"它变好意味着什么业务量在动",以及"它可能是假的吗"。AUC 0.93 要翻译成"名单前 10% 的客户里,实际流失率比总体高多少"。如果翻译不出来,这个数字就是装饰。**检查动作**:在模型卡或 PR 里,指标后面跟着一句业务陈述;拿不到这句陈述,就不要把指标写进任何汇报。

**五、上线前写下监控假设。**上线之前,明确写出三件事:哪个量会证明模型在起作用、多久之后开始看、如果没起作用什么时候下线。模型上线后无人监控,等于一次性项目——它会一直运行,慢慢腐烂,直到某天有人发现它早就不预测任何东西了。**检查动作**:监控假设和回滚阈值在上线 PR 里,不是"以后补"。

## 7. 怎么读这本书

Part I 的五章共用一套结构,每章五段,顺序是刻意的:

**业务问题**——先讲清楚"什么业务会死在这"。不解决它,后面所有技术细节都是空转。**原理门槛**——手写最小实现,目的是让你知道 AI 会错在哪里,而不是让你戒掉库。**AI 工程版**——写作时真实生成的实现,带生成记录(提示词摘要、日期),成品经过审阅修正;错误是真的发生过,不是编出来的。**审阅对照**——用 `REVIEW-CHECKLISTS.md` 的原问题审上面两份代码,让你看到"审阅"具体长什么样。**仓库导航**——用本仓 `scripts/analyze.py` 和真实历史数据做练习,命令可以直接复制执行。

读法上有两个建议。**如果你只有半小时**:读本章,然后直接进 ch02(泄漏),因为它是 AI 最常犯的第一个错误,且后果最贵。**如果你正在审一份具体的 AI 产出**:跳到 ch04(指标),那章讲的是怎么把 AUC 翻译成钱。

Part I 的五章是一条闭环,不是五个话题:ch02 泄漏和 ch03 切分是同一类错误的两个来源——一个来自字段,一个来自边界;ch04 指标解决"这个模型值不值得上线";ch05 把前三章拼成一条完整的管线,收束到"审阅者的四个动作"。

本章的立场,落到具体类目上,就是这份清单覆盖的 39 个类目。跑一次导入,再用查询 CLI 看看数据:

```bash
/opt/homebrew/bin/python3 scripts/import_history.py   # 首次:187,281 行
/opt/homebrew/bin/python3 scripts/analyze.py data/history.db recent 5
```

第一条把 `history/` 下 208 个周快照导入本地 SQLite(约 6 秒,`data/history.db` 已被 gitignore,用完可随时重建);第二条打印最近加入的项目。Part I 后续各章会按主题给出更具体的查询,例如 `top ml-frameworks 5`、`top time-series-data 5`、`trend Tensorflow`。

立场素材的三个来源,建议按顺序读一遍:`config/header.md` 的 `## How to Use This List in the AI-Coding Era` 一节(四个姿态的原文,README 每次生成时把它嵌在正文之前)、`REVIEW-CHECKLISTS.md` 的引言(为什么要按领域给问题)、以及 `git log` 里 2026-10-03 那几次 commit(机器怎么管机械正确性)。
