# ch03 切分

> ch02 的泄漏来自**字段**。这一章的泄漏来自**边界**。同一个失效模式,第二个来源。

## 1. 业务问题:为什么 AI 默认给随机切分

让 AI 写一个预测模型的训练脚本,它给出的切分几乎总是这一行:

```python
train_test_split(df, test_size=0.2, random_state=42)
```

这行没有错。它干净、可复现、参数含义清楚,任何一本入门书都会这么写。问题在于它是一个**不需要你回答任何问题的切分**——而真实业务里,切分恰恰是第一个必须回答的问题。

设想一个设备故障预测的项目。表里有 60 台设备,每台 20 天的每日记录。模型上线后要做的事是:**给一台新装的、训练期里从没见过的设备,预测它明天坏不坏。** 这时候 `train_test_split` 做了什么?它随机挑了 20% 的行做测试集——**测试集里 60 台设备一台不少,全都也在训练集里。** 实测:

```
      训练/测试里同时出现的设备: 60 / 60
      测试行读到同设备『更晚』训练行的: 229 / 240 (95.4%)
```

第二行更糟。同一台设备在测试日之后的记录,也在训练集里。模型只要认得出"这台机器我见过",就能从它**未来**的行为里读出它**现在**的状态。这不是过拟合,这是把答案抄在了卷子上。

这类失败和 ch02 有一个共同点,也正是它危险的地方:**指标不会报警。** 一个用随机切分训练出来的设备模型,离线 AUC 是 0.80,周报里一切正常。上线之后,客户把 15 台新设备接进来,模型给它们的分数全部退化成同一个数——因为它压根没见过这些机器。没有人会在训练阶段发现这件事,因为训练阶段的测试集和上线后的世界根本不是同一个世界。

**随机切分的错误不是"数据太少"或"过拟合",是它默认了一个从未被验证的假设:测试样本和训练样本来自同一个总体,而且同分布。** 这个假设在教科书数据集上成立(那些数据集本来就是从一个大总体里随机抽的),在业务数据上几乎总是不成立。

而它之所以是 AI 的默认选择,原因很朴素:随机切分是**代码示例里最常见的**。训练集和测试集的关系,在入门教程里被简化成了"同一批数据的两个切片"。AI 学的是这个形状,它不会自动想到你的表里还有一台台设备、一个个用户、一个个客户,以及一条条按时间排下去的历史。

所以这一章要给你的不是"别用 `train_test_split`"——`train_test_split` 在合适的数据上是对的,ch05 会讲什么时候。给你的判据是清单上那一句话:**切分方式要匹配系统被使用的方式。** 这句话在动手切之前就要问,而不是切完看指标。

## 2. 原理门槛:三种切分,三个不同的结论

```bash
/opt/homebrew/bin/python3 docs/tutorial/code/ch03/splits_minimal.py
```

[splits_minimal.py](code/ch03/splits_minimal.py) 是纯标准库实现,只有 `math`、`random`、`sys`、`time` 四个 import——三个切分函数、两个估计器、AUC(秩和公式)全部手写。1200 行数据,跑完 0.8 秒。

数据集是构造的"设备故障预测",两层 group 结构加一条时间轴:

- **设备**是 group。同一台机器的多条记录共享一个"个体敏感度"——它天生就比别的机器容易坏。这个量**只能从这台设备自己的故障记录里学到**。
- **工厂**是 group 的 group。同一工厂的设备共享环境应力 `ambient`,这是设备之间的共同因子,也是"组间存在可测量的分布差异"的来源。
- **时间**有序,记录按"交付日 + 天"全局排序。

四个工厂的实际故障率,直接证实了这个共同因子:

```
    工厂   环境应力   故障率
    F0        0.15     8.67%
    F1        0.40    16.00%
    F2        0.65    21.33%
    F3        0.90    41.67%
```

数据构造上有一处刻意的安排值得说:**四座工厂按交付波次交错进场**,每 6 天各出一台设备。如果按工厂整块编号,工厂就和时间轴完全共线,那时序切分测到的偏移会是"我换了个工厂",而不是"时间往前走了"——两个效应混在一起,哪个都讲不清。交错之后,任何时间切片上四座工厂都在场,时序切分测的才真的是时间。

## 3. 三条线要分开修:时间、实体、分布

四种切分跑完,三个诊断量:

```
  切分                  训练/测试   组重叠      未来行泄漏    hours_z 均值差  ambient 均值差
  ------------------------------------------------------------------------------------------------
  random_split          960/ 240  60/60 100.0%   229 ( 95.4%)         -0.0341         -0.0247
  time_split            960/ 240  16/20  80.0%     0 (  0.0%)         -1.9942         +0.0000
  group_split(device)   960/ 240   0/12   0.0%     0 (  0.0%)         -0.2762         +0.1042
```

- **组重叠**:同一台设备同时出现在训练和测试的台数 / 测试集设备台数
- **未来行泄漏**:测试行里,存在"同一台设备、日子比它更晚"的训练行的行数
- **均值差**:训练均值 − 测试均值。接近 0 表示两半同分布,明显偏离表示切出了真实偏移

### 随机切分:两处泄漏,都测得到

`random_split` 那一行两个数就够了:**组重叠 60/60,未来行泄漏 229/240(95.4%)**。这两个量不需要任何机器学习知识,一行 pandas 就能算出来,十秒钟的工作量。

反过来看其余三行,`time_split` 的未来行泄漏是 0,两种 `group_split` 的组重叠是 0。**这就是"边界画错了"的全部内容**——注意 ch02 的泄漏藏在字段里,本章的泄漏藏在边界上,两者的排查手段完全不同。

### 时序切分:修好了方向,没修实体

`time_split` 把未来行泄漏清零了——模型看不到测试日之后的事。这一条修得干净。

但组重叠还是 16/20。四座工厂按波次进场,每台设备 20 天,时间上晚 20% 的测试期里,绝大部分老设备仍然横跨训练期和测试期。**时序切分只修时间那条线,实体那条线原封不动。** 报告里最容易出的错就是"我们做了时序切分",然后就以为泄漏问题解决了。

`hours_z` 均值差 −1.9942 是这一行最值得看的数字。时序切分测出训练和测试之间有巨大的分布偏移,这是真实的:测试期里的设备整体磨损得更厉害了。随机切分几乎测不到同样的偏移(−0.0341),因为它把磨损前后的记录打散在两边,两半的平均值自然接近。

**这就是随机切分最隐蔽的代价之一:它不光泄漏,还把分布漂移给平均掉了。** 漂移是真实存在的业务风险,随机切分会让你完全看不见它。

### group 切分:重叠归零,但这还不够

`group_split(device)` 的组重叠是 0,`ambient` 均值差 +0.1042——留出的设备群体和训练群体在环境上有轻微差异,这是随机留出 12 台设备的正常结果。

`group_split(factory)` 的 `ambient` 均值差是 **−0.5000**:测试集里只有环境应力最高的那座工厂,训练集里根本没有那个条件。重叠同样是 0。

**这两行的组重叠都是 0,但只有第二行测出了真实的分布偏移。** 所以"重叠 = 0"是及格线,不是及格。它证明了"同一条记录不会同时出现在两边",但没告诉你"训练集是否覆盖了上线时会遇到的条件"。后者要靠均值差、分位数、以及业务知识一起看。

同样值得说的是反向的对照:`time_split` 的 `ambient` 均值差是 **+0.0000**。因为四座工厂在时间上完全交错,时间切片天然包含全部四座工厂,时序切分**测不到工厂之间的差异**。

两条线,两种切分,互不替代:

| 切分 | 修好的线 | 测不到的 |
|---|---|---|
| `time_split` | 时间方向(未来行泄漏 95.4% → 0) | 实体重叠、工厂级共同因子 |
| `group_split` | 实体边界(组重叠 60/60 → 0) | 时间方向 |

## 4. 谁在受泄漏的影响:取决于模型能不能记住实体

上面三节都在讲切分质量。这一节讲一件更反直觉、也更重要的事:**泄漏到底抬不抬分,取决于模型。**

两个估计器被放在同一份数据、同一组种子下跑了四种切分:

```
  A 设备先验(记实体)   B 特征逻辑回归(只认特征)
  ------------------------------------------------------------
  random_split         A = 0.7794        B = 0.7982
  time_split           A = 0.5324        B = 0.7121
  group_split(device)  A = 0.5000        B = 0.7936
```

**A 设备先验**:测试行属于哪台设备,就用那台设备在训练集里的故障率预测;没见过就退回总体故障率。这不是傻模型——这是可靠性工程师上手第一个会做的东西,在"预测一台你已经在看的设备的明天"这个场景里,它是**对的**。它的全部能力都来自 group 结构。

**B 特征逻辑回归**:手写 sigmoid + 批量梯度下降,只用运行时长、振动、环境温度三个特征。它记不住实体。

现在看数字。

**A 在 group 切分下塌到 0.5000。** 因为它要的那台设备一台都没在训练集里出现过,300 条测试行全部退回常数,常数预测的 AUC 就是 0.5。代码把这件事打印出来了:

```
  group_split(device)  A 估计器有 240/240 条测试行退回总体故障率(该设备没在训练集里)
```

**这不是 bug,这是真能力被正确地否掉了。** 上线换新设备时,这个模型确实只能给常数。随机切分下的 0.7794 才是假的——它衡量的是"给一台见过的设备打分",不是"给一台新设备打分"。

**B 基本没动。** 0.7982 → 0.7936,差 0.0046。**所以本章不是"随机切分一定让指标虚高"。** 随机切分对不记实体的模型没有系统性乐观,反而因为同类样本在测试集里被稀释而略微吃亏。

诚实的结论只有一句:**切分泄漏只对会记住实体的模型抬分。** 而这类模型恰恰是最容易被业务接受的那个——它的预测结果好解释("这台机器最近老坏"),而且在演示时效果最好。

**这就是"默认切分不能是随机的"的真正理由:不是因为随机一定虚高,而是因为你事先不知道线上跑的是哪种模型。** 你要么两种切分都报,要么在上线场景的切分上报。报错了的那种,损失的是 0.28 的 AUC,以及一个上线三周后才发现的故障。

## 5. AI 工程版:sklearn 的三种切分器,和那行没改的代码

```bash
/opt/homebrew/bin/python3 docs/tutorial/code/ch03/splits_engineered.py
```

[splits_engineered.py](code/ch03/splits_engineered.py) 是同一份数据集的 sklearn 版本,文件头带生成记录(2026-10-03,提示词摘要写在 docstring 里)。它从 `splits_minimal.py` 直接 import `make_dataset`,所以两份代码的数字逐位一致。

它**故意保留了一处真实陷阱**:`main()` 里的路径 1 就是原始 AI 产出的那一行,一字未改。

```python
def ai_default_split(X, y, groups, factory_groups, time_key):
    """⚠️ 陷阱所在:原始 AI 产出,一字未改。

    这是代码示例里最常见的一行切分。它没问过两件事:
      1. 数据里有没有实体(同一台设备的多条记录)?
      2. 数据是不是按时间排的?
    两个问题的答案在这份数据里都是"有"。而这一行不打算知道。
    """
    idx = np.arange(len(y))
    train_idx, test_idx = train_test_split(idx, test_size=TEST_SIZE, random_state=42)
    return train_idx, test_idx
```

注意签名:`ai_default_split` 收到了 `groups` 和 `time_key` 两个参数,却**一次也没用**。这就是这件事的全部形态——数据里该有的信息全都摆在签名里了,切分函数只是不看。

四条路径跑完:

```
  切分                              组重叠      未来行泄漏     hours_z 均值差  ambient 均值差
  --------------------------------------------------------------------------------------------------
  路径 1  train_test_split(AI 默认)    60/60 100.0%   229 ( 95.4%)         +0.0240         -0.0195
  路径 2  GroupShuffleSplit(按设备)      0/15   0.0%     0 (  0.0%)         +0.0761         -0.0778
  路径 3  TimeSeriesSplit(最后折)       16/20  80.0%     0 (  0.0%)         -1.9942         +0.0000
```

sklearn 提供了三个切分器,它们解决的是**三个不同的问题**,不是同一个问题的三种口味:

- `GroupShuffleSplit(groups=...)` 修实体边界。传设备号就得按设备留出,传工厂号就得按工厂留出——**参数就是你的业务语义的入口**,这正是 AI 默认产出缺的那一环。
- `TimeSeriesSplit` 修时间方向。但它**按行号切**,前提是 X 已经按时间排好。数据从数据库里捞出来通常按主键排,不是按时间排,而 `TimeSeriesSplit` 不检查、不警告,照切不误。忘了排序这一条,你会得到一个看起来很正常、实际上没有任何时间意义的切分。
- 路径 3 打印的折规模提醒了另一件事:

```
    折 1  训练 240 行 / 测试 240 行
    折 2  训练 480 行 / 测试 240 行
    折 3  训练 720 行 / 测试 240 行
    折 4  训练 960 行 / 测试 240 行
```

滚动窗口的每一折都在增长,这是时序 CV 的正确形态。但注意路径 3 的组重叠仍然是 16/20——**它只修了时间那条线。** sklearn 提供了工具,选哪条线是你的责任。

### 泄漏不改变模型,只改变测试集

路径 1 和路径 2,模型结构一字未改,只换切分:

```
  设备先验   AUC 0.8048 -> 0.5000  (-0.3048)
  逻辑回归   AUC 0.8006 -> 0.8439  (+0.0433)

  逻辑回归系数(路径 1 训练 / 路径 2 训练,同一个 Pipeline 结构):
    hours_z          +0.9364 ->   +0.8260
    vibration_rms    +0.5858 ->   +0.5943
    ambient          +0.5126 ->   +0.4513
```

三个数字,三件不同的事,别把它们混成一句:

**第一,系数基本没动。** 这和 ch02 的结论正好相反——ch02 那处标准化泄漏能从权重表上看出来(`age` 系数差 1.41%),本章的切分泄漏**看权重表一点都看不出来**,因为泄漏不在字段里,在边界上。ch02 那套"打印权重表放进 PR"的检查,在这一章完全失效。

**第二,设备先验从 0.8048 塌到 0.5000。** 它需要的每一条测试信息,在 `GroupShuffleSplit` 下它一条都拿不到。

**第三,逻辑回归不但没掉,还涨了 0.0433。** 别把这读成"group 切分更保守所以更差"——它变好是因为 group 切分顺手干掉了另一件好事:测试设备不再在训练集里出现,同类样本不再被稀释。两种效应方向相反,净结果是正的。

这也和 ch02 形成一组对照,值得放在同一张桌子上看:

| | ch02 标准化泄漏 | ch03 切分泄漏 |
|---|---|---|
| 泄漏在哪 | 参数统计量 | 切分边界 |
| 系数变了吗 | 变了(`age` +1.41%) | 几乎没变 |
| 测试 AUC 变了吗 | 没变(逐位相同) | 大变(−0.30 ~ +0.04) |
| 怎么发现 | 对比两次 `fit` 的 mean_ | **只能靠算组重叠** |

**没有一种单一检查能同时抓到这两类泄漏。** 这是本章相对 ch02 最重要的增量:你的检查清单得有两套动作,一套查字段,一套查边界。

>

>

> - [ ] What exactly is being predicted, and does the label exist at prediction time in production? (If not: target leakage.)
> - [ ] **How is the data split — random, temporal, grouped by entity? Does the split match how the system will be used?**

这一章整章都在回答加粗那一条。它和 ch02 用的第一条是同一份清单里的邻居,但**两者的排查动作完全不能互相替代**:

- 第一条问的是**表结构**。列出全部特征,逐个问"预测时点拿得到吗"。ch02 的三个泄漏全在这一步被拦住。
- 这一条问的是**边界**。切完之后问"训练和测试之间隔开了什么"。本章的泄漏全在这一步被拦住。

**注意第二条的后半句比前半句重要。** "How is the data split — random, temporal, grouped by entity?" 是三个选项,列出来就完了,对着勾一个。"Does the split match how the system will be used?" 才是真正的工作量:你需要能说出一句话,描述系统上线后**第一条预测请求**长什么样,然后把切分画到那句话上。

设备故障预测那句话是:**"给一台 11 月才装的设备打分,这台设备在 10 月的故障记录一条都没有。"** 对着这句话看表:

| 切分 | 对上了吗 |
|---|---|
| `random_split` | ✗ 测试集里 60 台设备训练集里全有 |
| `time_split` | ✗ 上线是新设备,不是老设备的后续;16/20 设备训练时已存在 |
| `group_split(device)` | ✓ 测试集是训练集里没有的 12 台设备 |
| `group_split(factory)` | ✓✓ 连环境条件都是新的——比上线场景还严 |

**这张表就是这条问题的实际用法。** 四个切分全都能跑,全都不报错,区别只在你有没有把上线场景写成一句话。

还要说清楚一件事,免得下结论走偏:**`group_split` 也不是免费的正确。** 按设备留出测的是"新设备"这个场景。如果你的系统实际是"给已在役的设备持续打分"(这在可靠性监控里更常见),那按设备留出就**过度严格**了——你会把一个上线后好用的模型报成一个看起来不行的模型。

所以正确做法不是"换成 group 切分",是**先写出上线那句话,再决定边界画在哪**。可能你需要同时报两套:`GroupShuffleSplit` 给上线前的模型选择,滚动窗口留出给上线后的监控基线。两个数字都要在,不要只留好看的那个。

至于清单里其余几条,ch02 已经逐条对过一遍,本章不重复。只需要补一句:**"What baseline does this beat?" 这一条在切分有问题的时候会给出错误答案。** 设备先验在随机切分下 0.7794,在 group 切分下 0.5000——后者不是"它很差",而是"它在这个场景里没有信息可用"。基线比较必须在**和上线一致的切分**上做,否则你比较的是两个不同问题。

## 本章检查动作

回到 ch02 说的那句:从 ch02 起,每章的手写实现都放在 `docs/tutorial/code/<章号>/<章号>_minimal.py`,用 `/opt/homebrew/bin/python3` 直接跑通。这一章打印的是**切分质量表**。

审阅一份 AI 产出的模型代码时,切分部分按这个顺序做:

- **先写上线那句话,再读切分代码。** "上线后第一条预测请求长什么样?"——能写出来才有资格评价切分,写不出来说明需求还没定,切分无从谈起。
- **算组重叠。** `len(set(train[entity]) & set(test[entity]))`。非零就是泄漏,这一条不依赖任何模型,不需要跑训练。
- **算未来行泄漏。** 测试行里有多少条存在"同实体、日期更晚"的训练行。`time_split` 下它必须是 0。
- **看均值差,不只是看重叠。** 重叠归零是及格线。训练和测试的分布是否一致,是另一件事。
- **两种切分都报。** 时间和实体是两条独立的线,只修一条不等于修好。业务上确实是"持续给老设备打分"的话,说明按设备留出过度严格,需要同时报滚动窗口基线。
