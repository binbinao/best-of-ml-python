# Repository Guidelines

## Project Overview

`best-of-ml-python` is a weekly-updated ranked list of machine-learning Python libraries (~950 projects, 39 categories). This is a data/config repository with a thin maintenance layer — three standalone Python scripts (`scripts/validate.py`, `scripts/import_history.py`, `scripts/analyze.py`) plus their pytest suite — and no application runtime. The single source of truth is `projects.yaml`; `README.md`, `latest-changes.md`, and everything in `history/` are machine-generated by the external [`best-of-generator`](https://github.com/best-of-lists/best-of-generator), invoked weekly via GitHub Actions. Generator/metadata-collection bugs belong upstream, not here.

## Architecture & Data Flow

```mermaid
flowchart LR
    A[projects.yaml<br/>human-edited data] --> C[best-of-update-action@v0.8.5<br/>GitHub Actions, weekly]
    B[config/header.md + footer.md<br/>README framing templates] --> C
    C --> D[README.md<br/>header + generated body + footer]
    C --> E[latest-changes.md<br/>trending digest -> draft release body]
    C --> F[history/YYYY-MM-DD_projects.csv<br/>YYYY-MM-DD_changes.md]
```

- `projects.yaml` has four top-level keys, in order: `configuration`, `categories`, `labels`, `projects`.
- README = `config/header.md` (with `{project_count}`, `{stars_count}`, `{category_count}` placeholders filled) + auto-generated TOC/legend/category body + `config/footer.md`.
- Ranking is automatic: projects are scored by a project-quality score (GitHub + package-manager metrics) computed by the generator. Humans never order entries.
- CI validates `projects.yaml` (`scripts/validate.py`), writes outputs to an `update/<VERSION>` branch, tags `<VERSION>`, opens a PR to `main` via `gh`, and creates a draft release via `gh release create` using `latest-changes.md` as the body.

## Key Directories

| Path | Purpose |
|---|---|
| `projects.yaml` | Core data: configuration, categories, labels, and all project entries |
| `config/` | `header.md`/`footer.md` README templates; `images/` |
| `history/` | Weekly snapshots: `YYYY-MM-DD_projects.csv` (full metric dump) + `YYYY-MM-DD_changes.md` |
| `.github/` | `workflows/update-best-of-list.yml`, `ISSUE_TEMPLATE/`, `PULL_REQUEST_TEMPLATE.md` |
| `scripts/` | `validate.py` (projects.yaml checks — also the CI gate), `import_history.py` (history CSVs → SQLite), `analyze.py` (query CLI) |
| `tests/` | pytest suite for the scripts: `test_validate.py`, `test_history.py` |
| `docs/tutorial/` | 教程正文与可运行示例(chXX 代码目录,验收:`python code/chXX/chXX_minimal.py`) |
| `data/` | Gitignored local artifact: `history.db`, rebuilt on demand via `import_history.py` |
| `README.md`, `latest-changes.md` | Generated output — never hand-edit |

## Development Commands

There is no build system, Makefile, or package manifest. Local tooling is a set of standalone Python scripts plus a pytest suite, run from the repo root with `/opt/homebrew/bin/python3` (the interpreter that has PyYAML — the only third-party dependency, needed by `validate.py` and the tests; `import_history.py`/`analyze.py` are stdlib-only):

- **Validate `projects.yaml`** — run before any change to it; the same script gates CI before generation:

  ```bash
  /opt/homebrew/bin/python3 scripts/validate.py [path/to/projects.yaml]
  ```

- **Build the local history DB, then query it** — `data/history.db` is gitignored; rebuild it on demand:

  ```bash
  /opt/homebrew/bin/python3 scripts/import_history.py               # history/ -> data/history.db
  /opt/homebrew/bin/python3 scripts/analyze.py <db> <cmd> [args...]   # db is required
  #   top <category> <N>   top-N projects in a category (latest week, by projectrank)
  #   trend <name>         weekly (week, star_count, projectrank) trajectory
  #   recent <N>           most recently added projects
  #   status <name>        latest-snapshot fields for one project
  ```

  Real invocations against the local DB:

  ```bash
  /opt/homebrew/bin/python3 scripts/analyze.py data/history.db top ml-frameworks 10
  /opt/homebrew/bin/python3 scripts/analyze.py data/history.db trend PyTorch
  /opt/homebrew/bin/python3 scripts/analyze.py data/history.db recent 5
  /opt/homebrew/bin/python3 scripts/analyze.py data/history.db status transformers
  ```

- **Run the tests** (14 cases: `test_validate.py` ×10, `test_history.py` ×4):

  ```bash
  /opt/homebrew/bin/python3 -m pytest tests/ -v
  ```

The only "build" proper is the GitHub Actions workflow (`.github/workflows/update-best-of-list.yml`):

- **Scheduled**: cron `0 14 * * 4` (Thursdays 14:00 UTC).
- **Manual**: `workflow_dispatch` with optional `version` input (default `YYYY.MM.DD`; falls back to `YYYY.MM.DD-HH.MM` if the tag exists).
- Requires repo secrets `LIBRARIES_KEY` and `GITHUB_TOKEN`.

Full local regeneration requires the upstream `best-of-generator` CLI and a `libraries.io` API key — see its repo docs; nothing in this repo wires that up.

## Code Conventions & Common Patterns

### Project entry schema (`projects:` list)

Required: `name` (unique across the list), `github_id` (`owner/repo`; enforced by `require_github: True`). Typical entry:

```yaml
- name: PyTorch
  github_id: pytorch/pytorch
  pypi_id: torch
  conda_id: pytorch/pytorch
  docs_url: https://pytorch.org/docs/stable/index.html
  category: ml-frameworks
  labels: ["pytorch"]
  license: BSD-3-Clause
```

Optional keys seen in the data: `pypi_id`, `conda_id` (channel-prefixed when non-default, e.g. `conda-forge/x`), `dockerhub_id`, `npm_id`, `maven_id`, `helm_id`, `brew_id`, `apt_id`, `yum_id`, `snap_id`, `docs_url`, `category`, `labels`, `license` (manual override), `description`, `show` (force display), `resource: true` + `homepage` (collection/resource entries, not libraries).

### Naming & structural patterns

- Category IDs are kebab-case (`ml-frameworks`, `data-viz`, `nlp`); defined in the `categories:` block with `title` + `subtitle` (no `description` key). `ignore: True` hides a category from the README (e.g. `chinese-nlp`).
- In addition to the original 34, five AI-era categories extend the taxonomy (39 total): `llm-frameworks`, `agent-frameworks`, `rag-vectordb`, `inference-serving`, `model-hub`. `model-hub` is currently empty (0 projects) — it stays defined so the first qualifying entry can land there.
- Labels are lowercase IDs matching the `labels:` block. Valid IDs (17): `tensorflow`, `sklearn`, `pytorch`, `mxnet`, `spark`, `jupyter`, `paddle`, `pandas`, `jax`, `spacy`, `huggingface`, `keras`, `xgboost`, `llm`, `agent`, `rag`, `inference`.
- Unset `category` → project lands in the auto-generated `Others` bucket (explicit `category: others` is also accepted).
- `configuration:` block gates listing: `min_stars: 300`, `require_github: True`, `allowed_licenses` (Unlicense, Apache-2.0, MIT, BSD-3/2-Clause, ISC, MPL-2.0, LGPL-2.1 — outside this set renders a ⚠️ warning, not exclusion), `max_trending_projects: 10`.

### Contribution rules (from `CONTRIBUTING.md` + PR template)

- Edit **only** `projects.yaml` (or `config/header.md`/`footer.md` for framing text). Never edit `README.md`, `latest-changes.md`, or `history/` — they are generated.
- One project per PR/issue; titles: `Add project: <name>` / `Update project: <name>`.
- PR template requires checking a change-type box, a description (name + short blurb for new projects), and confirming you did not modify `README.md`.
- Prefer opening an issue from `.github/ISSUE_TEMPLATE/` (`add-project`, `update-project`, category, configuration, other) for discussion first.

## Important Files

- `projects.yaml` — the only file most changes touch
- `config/header.md` / `config/footer.md` — README framing (hand-edited; start with `<!-- markdownlint-disable -->`)
- `.github/workflows/update-best-of-list.yml` — the entire build pipeline (based on `best-of-update-action@v0.8.5`)
- `scripts/validate.py`, `scripts/import_history.py`, `scripts/analyze.py` — local validator, history importer, query CLI
- `CONTRIBUTING.md` — canonical add/update workflow and project-property docs
- `.github/PULL_REQUEST_TEMPLATE.md`, `.github/ISSUE_TEMPLATE/` — contribution intake
- `.github/.gitattributes` — `* linguist-language=Python`; marks `README.md`, `latest-changes.md`, `history/**` as `linguist-generated`

## Runtime/Tooling Preferences

- **No application runtime**: the only Python source is the maintenance layer (`scripts/`, `tests/`) — standalone scripts with no `pyproject.toml`/`requirements.txt`, no Node/Bun, no package manager. Do not add toolchain scaffolding.
- Generation runs on `ubuntu-latest` inside `best-of-lists/best-of-update-action@v0.8.5`; pinned versions in the workflow (`actions/checkout@v4`, `peterjgrainger/action-create-branch@v3.0.0`, `stefanzweifel/git-auto-commit-action@v4`) should only change deliberately. PR and draft-release creation use the runner's preinstalled `gh` CLI (`gh pr create`, `gh release create`) — not `hub` or `actions/create-release@v1`.
- `.gitignore` is a generic Python template; generated artifacts (`README.md`, `history/`) are intentionally committed, while `data/` (the local history DB) is gitignored and rebuilt on demand.

## Testing & QA

- `scripts/validate.py` gates CI: the workflow's `validate-projects-yaml` step runs it right before the generator step, so a bad `projects.yaml` fails the run before any output is produced.
- A pytest suite exists: `tests/test_validate.py` (10 cases) + `tests/test_history.py` (4 cases) — `/opt/homebrew/bin/python3 -m pytest tests/ -v`.
- `validate.py` rule list (run it locally before any `projects.yaml` change):
  1. The file parses as YAML and the top level is a mapping.
  2. All four top-level keys are present: `configuration`, `categories`, `labels`, `projects`.
  3. Every project has a `name`, and `name`s are unique across the list.
  4. `github_id` is present and shaped like `owner/repo`.
  5. A set `category` must be defined in the `categories:` block — the implicit `others` fallback is always valid.
  6. A set `labels` must be a list, and every entry must be a defined label ID.
- Project-level errors print as `projects.yaml: project '<name>': <error>` (no line numbers); the script exits non-zero and ends with an `OK` / `<N> error(s)` summary line.
- Markdownlint is not enforced; generated files carry `markdownlint-disable` directives — leave them in place.
